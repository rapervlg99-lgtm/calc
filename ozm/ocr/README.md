# Локальное извлечение таблиц из строительных PDF

PoC для извлечения сложных таблиц («Спецификация металлопроката» и подобных)
из листов проектной документации в структурированные данные.

**Полностью локально.** Никаких обращений к OpenAI / Claude / Gemini / Azure и
любым другим внешним сервисам в коде нет. Всё, что нужно, — Python-библиотеки и
шрифты, уже установленные в системе. Модели из интернета не скачиваются.

---

## 1. Что оказалось внутри тестового PDF

Прежде чем выбирать инструменты, страница была разобрана по объектам:

| Что смотрели | Что нашли |
|---|---|
| Страниц | 1, формат 2526 × 1191 pt (А1, альбом), producer `iLovePDF` |
| Растр | одна картинка 383 × 113 px — только логотип в штампе |
| Векторные объекты | **325 259** отрезков + 61 залитый прямоугольник |
| Линовка таблиц | 113 горизонтальных + 70 вертикальных линий (после склейки) |
| Текстовый слой | всего 164 span / 856 символов |

**Вывод: страница векторная, не растровая.** Но текстовым слоем покрыта лишь
малая часть содержимого: шапки, номера позиций (№ п.п.), подписи
«Итого» / «Всего профиля» и часть наименований профилей. Значения масс,
обозначения профилей (`Гн.□160х6`, `t12`, `16П`, `L 100х7`), марки стали
(`С355-5`) и номера ГОСТ — это **«взорванный» текст**: при экспорте из
AutoCAD/Revit шрифт разложен в микро-полилинии. Отсюда и 325 тысяч отрезков.

Дополнительно: одна ячейка может быть частично текстом, частично векторами.
У «Профили стальные гнутые замкнутые сварные квадратные ГОСТ 30245-2003»
первые две строки лежат в текстовом слое, остальные четыре — в геометрии.

### Почему ломается кириллица

Диагноз точный, не предположение.

Три шрифта объявлены как `Type0` / `Encoding = Identity-H`,
`CIDToGIDMap = /Identity` и **без словаря `/ToUnicode`**:

```
9  << /BaseFont /YHNSRZ+ArialMT /Encoding /Identity-H /Subtype /Type0 ... >>
10 << /CIDSystemInfo ... /CIDToGIDMap /Identity /Subtype /CIDFontType2 ... >>
```

Коды в потоке содержимого — это не Unicode и не WinAnsi, а **прямые glyph id
исходного шрифта**. У встроенных сабсетов при этом:

* нет таблицы `cmap` (обратного отображения glyph → Unicode);
* таблица `post` формата 3.0, то есть имён глифов тоже нет.

Информации о Unicode в документе физически не осталось. Любой экстрактор
вынужден догадываться; PyMuPDF трактует CID как codepoint, поэтому «Всего»
превращается в `ȼɫɟɝɨ`, а пробел (glyph id 3) — в символ `0x03`.
`pdftotext` и `pdfplumber` дают тот же мусор по той же причине.

### Как это исправлено детерминированно

Сабсет сохраняет **нумерацию глифов исходного** шрифта (4548 глифов ≈ полный
ArialMT). Значит достаточно взять оригинальный шрифт из системы, построить по
его `cmap` отображение unicode → gid и обратить его.

Догадка проверяется **независимо, двумя способами**:

1. PDF хранит массив `/W` — ширины по CID. Для ArialMT ширины совпали с
   системным `arial.ttf` в **40 из 40** случаев.
2. Когда `/W` нет (ISOCPEUR, GOST Common), сверяется число глифов сабсета:
   597 = 597 и 659 = 659.

Мэппинг принимается только при успешной проверке; иначе шрифт помечается как
невосстановимый и его текст уходит в векторный распознаватель. На тестовом
листе после ремонта **не осталось ни одного повреждённого span**.

## 2. Выбранный конвейер

```
PDF
 ├─ fontfix        ремонт кодировки текстового слоя (glyph order + проверка ширин)
 ├─ vector_grid    линовка из ВЕКТОРОВ -> сетка -> merged cells
 │   └─ cv_grid    резерв: морфология по растру (для сканов)
 ├─ glyph_ocr      «взорванный» текст: контуры -> шаблоны глифов
 │   └─ ocr_backends  резерв: RapidOCR / Tesseract / гибрид (сканы, чертёжный шрифт)
 ├─ cell_reader    приоритет источников: текстовый слой > векторы > OCR
 ├─ structure      шапка -> роли колонок, строки, деление на логические таблицы
 ├─ normalizer     числа, ГОСТ/ТУ, обозначения профилей
 ├─ validator      детерминированный пересчёт всех итогов
 └─ exporter       JSON / XLSX / CSV / debug PNG / отчёт
```

Ключевые инженерные решения и почему именно так:

**Геометрия — из векторов, а не по Hough/морфологии.** Линовка в этом PDF —
настоящие объекты с точными координатами. Не нужно подбирать порог
бинаризации, тонкие линии 0.6 pt не теряются, а **merged cells
восстанавливаются строго**: ячейки объединяются там, где разделителя
физически нет, а не по эвристике «справа пусто».

Попутно выяснились три особенности листов, которые пришлось обработать:

* у левой таблицы **нет левой границы** — все горизонтали начинаются с
  x = 144, а самая левая вертикаль стоит на x = 228.8. Без восстановления
  неявной границы терялась первая колонка целиком;
* строки поз. 26 и 27 **не разделены линией**. Шаг строк в таблице постоянный
  (22.68 pt), поэтому пропущенные разделители достраиваются там, где зазор
  кратен шагу. Иначе все последующие номера позиций «съезжали»;
* **рамка листа отличается от линовки не длиной, а положением.** Рамка
  исключается из группировки линий, иначе она сшивает всю страницу в один
  блок. Отбирать её по одной длине нельзя: на листе-скане «Техническая
  спецификация металла» таблица занимает почти весь лист, её собственные
  вертикали длиной 778 pt при высоте листа 842 pt отбрасывались вместе с
  рамкой, и из 10 колонок оставалось 6 — марка стали, номер профиля, № п.п. и
  «Колонны/Стойки» слипались в одну ячейку. Теперь длина проверяется вместе с
  положением: рамка идёт вдоль края листа, разделитель внутри таблицы — нет.

**Распознавание — сопоставление с шаблонами, а не нейросетевой OCR.** Растр
здесь синтетический: он получается рендером векторов, то есть без шума,
перекосов и JPEG-артефактов, с любым нужным DPI. Начертание — обычный Arial
(шапка колонок — Arial Narrow). В такой постановке шаблоны, отрендеренные из
того же шрифта и в том же кегле, точнее общего OCR и вдобавок дают честный
confidence, точные координаты каждого символа и никакого «умного» автокорректа,
который ломает `C255-4` или `Гн.□100х4,5`.

**Вертикальные подписи читаются с поворотом.** Подписи колонок «по элементам
конструкций» («Колонны/Стойки», «Балки», «Связи», «Прогоны») набраны снизу
вверх. Общий вызов OCR на область таблицы разбирает их на одиночные знаки
(«Балки» -> «5 а 8 a}») либо даёт латинскую кальку RapidOCR («Прогоны» ->
«poroHbl»). Ячейка заметно выше, чем шире, перечитывается на кропе, повёрнутом
на 90° по часовой; берётся вариант, где кириллицы больше. Против часовой не
пробуем — подпись встаёт вверх ногами.

Проверено на этом файле, а не взято из общих соображений: **RapidOCR
(PP-OCRv4) базовой модели не знает кириллицы** — «Итого» читается как
`MTOrO`, «Рельсы крановые» как `PenbCbl KpaHOBble`. Цифры он берёт верно
(`13,04`), но для русских проектных таблиц непригоден. Tesseract с `rus`
кириллицу знает, но требует внешнего бинарника и заметно хуже разбирает
обозначения и массы. Поэтому основной растровый режим — `--ocr hybrid`: оба
движка на одной области, каждый на своей половине таблицы (см. §8).

**Тяжёлая VLM не подключалась.** Она здесь не нужна и противоречила бы
требованию проверяемости: LLM не должна ни считать итоги, ни угадывать
обозначения.

**Семантическое ограничение алфавита.** Роль колонки определяет допустимый
набор символов: в колонках масс возможны только цифры, запятая, точка и минус.
Латиница из алфавита почти полностью исключена — в русских спецификациях её
нет, зато `C/С`, `P/Р`, `O/О`, `x/х` неотличимы по начертанию (пока латиница
была в наборе, `С255-4` читалось как `G255-4`, а `ГОСТ` как `ГОGТ`).
Оставлены только `L` (уголок) и `t` (толщина листа).

## 3. Установка

Требуется Python 3.10+ (проверено на 3.12) и установленные системные шрифты
Arial / Arial Narrow (Windows — по умолчанию; Linux — пакет
`ttf-mscorefonts-installer` либо Liberation Sans, они тоже поддерживаются).

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Растровый OCR-резерв — нужен для сканов и для листов с чертёжными
одноштриховыми шрифтами:

```bash
pip install rapidocr-onnxruntime          # PP-OCRv4, ONNX; кириллицу НЕ знает
winget install UB-Mannheim.TesseractOCR   # знает кириллицу
pip install pytesseract
```

Ставить стоит оба: режим `--ocr hybrid` (и `--ocr auto`, когда доступны оба)
использует их вместе — иначе останется один движок со своей слабой стороной.

Внимание: тихая установка Tesseract кладёт только `eng`. Русский язык надо
доставить отдельно — положить `rus.traineddata` (~4 МБ,
`github.com/tesseract-ocr/tessdata_fast`) в папку `tessdata/` в корне проекта.
Код сам находит её и выставляет `TESSDATA_PREFIX`; права администратора не
нужны, и папка целиком уезжает в Docker-образ. Если файла нет, бэкенд честно
предупредит и переключится на английский.

Путь к языковым файлам передаётся переменной окружения, а НЕ флагом
`--tessdata-dir`: pytesseract разбивает config по пробелам, и путь с пробелами
(тем более с кириллицей) разваливается на части.

## 4. Запуск

```bash
python app.py "4_PIR2815_25_KR-37 (1)-1.pdf" --output ./result
```

Полезные ключи:

```bash
python app.py input.pdf -o ./result --pages 1-3          # только часть страниц
python app.py input.pdf -o ./result --dpi 450            # выше DPI распознавания
python app.py input.pdf -o ./result --ocr auto           # включить растровый резерв
python app.py input.pdf -o ./result --ocr hybrid         # текст Tesseract + числа RapidOCR
python app.py input.pdf -o ./result --all-glyphs         # трассировка по всем символам
python app.py input.pdf -o ./result --tol-per-term 0.01  # ослабить допуск проверок
```

Код возврата: `0` — все арифметические проверки пройдены, `1` — есть
расхождения (удобно для CI), `2` — файл не найден.

### Веб-интерфейс

Если удобнее «положить файл и посмотреть результат», есть локальная страница:

```bash
python webapp.py --open
```

Открывается `http://127.0.0.1:8000/`. Перетащили PDF или выбрали его кнопкой —
страница показывает имя и размер файла; распознавание начинается только по
кнопке «Распознать», до этого файл можно заменить («Заменить файл» или просто
перетащить другой) и поправить настройки. Дальше — распознанные
таблицы в том виде, как они нарисованы на чертеже (с объединёнными ячейками),
подсветку спорных значений и строк с расхождением в арифметике, все проверки с
пересчётом, отладочное изображение страницы и кнопки выгрузки XLSX/JSON/CSV.
При наведении на ячейку показываются источник значения, confidence и все
применённые правки.

Чтобы отдать тот же интерфейс за reverse proxy на пути `/ocr`
(так подключено в calclab.pro):

```bash
python webapp.py --port 8090 --base-path /ocr
```

Страница и API тогда живут по `http://127.0.0.1:8090/ocr/`. Без `--base-path`
поведение прежнее: корень `/` и `/api/...`.

Сделан на стандартной библиотеке — **дополнительных зависимостей не требует**.
Страница самодостаточна: ни одного внешнего CSS/JS/шрифта, запрещено политикой
CSP. Сервер слушает только `127.0.0.1`, аутентификации нет — поэтому `--host`
менять стоит только осознанно. Загруженные документы лежат во временном
каталоге и удаляются через 6 часов.

Тот же результат доступен как HTTP API — это и есть точка встраивания в backend:

```
POST /api/extract              multipart/form-data, поле file  -> JSON с результатом
GET  /api/job/<job>                                            -> тот же JSON повторно
GET  /api/file/<job>/<имя>                                     -> XLSX / JSON / CSV / PNG
```

Дополнительные поля формы: `pages`, `dpi`, `low_conf`, `all_glyphs`, `ocr`.
Список доступных OCR-движков отдаёт `GET /api/capabilities` — интерфейс по нему
помечает неустановленные и показывает предупреждения (например, что базовая
модель RapidOCR не знает кириллицы). Гибрид доступен, только когда установлены
оба движка.

**По умолчанию в интерфейсе выбрано «Авто»** — берётся лучший доступный движок
(при установленных Tesseract и RapidOCR это гибрид). OCR при этом запускается
НЕ на всём листе, а только на блоках, которые не удалось прочитать по векторам,
поэтому на хороших чертежах он почти не включается.

Замеры, на которых основано это решение:

| Лист | без OCR | «авто» (гибрид) |
|---|---|---|
| КР-37, хороший вектор | 22,8 с; спорных 36; 2 блока нечитаемых | 33,9 с; спорных **21**; нечитаемых **0** |
| КМ, чертёжный шрифт, нет текстового слоя | 40,5 с; спорных 97; 2 блока нечитаемых | 68,9 с; спорных **21**; нечитаемых **0** |

Три основные таблицы КР-37 при этом не меняются ни на символ: они проходят
порог качества и до OCR не доходят. Цена — примерно в 1,5 раза больше времени.

В CLI и в библиотеке значение по умолчанию осталось `none`: там важнее
предсказуемость, скорость и отсутствие внешних зависимостей. Для тех же
результатов, что в интерфейсе, укажите `--ocr auto`.

Блок, содержимое которого распознать не удалось, показывается не пустой сеткой,
а пояснением с причиной и подсказкой: включить OCR (если таблица вставлена
картинкой) либо игнорировать (если это штамп с повёрнутым текстом).

Замечание по портам: на Windows часть диапазонов зарезервирована Hyper-V/WSL, и
`bind` падает с `WinError 10013`, хотя порт свободен (проверить —
`netsh interface ipv4 show excludedportrange protocol=tcp`). Поэтому при
занятом порте сервер сам берёт следующий свободный из списка и печатает
итоговый адрес.

Тесты:

```bash
python -m pytest tests -q
```

`tests/test_units.py` (52 теста) не требует PDF. `tests/test_integration.py`
(30 тестов) сверяет распознанные значения с эталоном, снятым с чертежа глазами;
путь к образцу задаётся переменной `OCRPDF_SAMPLE`, иначе тест пропускается.

### Сколько это занимает

Замеры на приложенном листе А1 (2526 × 1191 pt, 325 тыс. векторных отрезков,
1090 ячеек), CPU, без GPU:

| Этап | Время |
|---|---|
| ремонт кодировки шрифтов | 0.03 с |
| извлечение линовки | 0.6 с |
| поиск блоков и построение сетки | 0.02 с |
| рендер страницы 350 DPI (12280 × 5790 px) | 0.14 с |
| контуры глифов + калибровка гарнитуры/кегля | 6.5 с |
| чтение 991 ячейки (распознавание) | 2.8 с |
| **полный прогон, включая выгрузку** | **~10 с** |

Время определяется **числом векторных контуров**, а не размером страницы:
рендер занимает доли секунды, а основная работа — сопоставление ~3700 контуров
с шаблонами. Лист с текстовым слоем без «взорванного» текста обрабатывается за
доли секунды: распознавать нечего. Скан пойдёт через растровый OCR, там время
задаёт уже выбранный движок.

Влияние DPI (то же качество проверок, разное число спорных ячеек):

| DPI | Время | Ячеек на ручную проверку |
|---|---|---|
| 200 | 7.7 с | 109 |
| 250 | 6.6 с | 36 |
| 300 | 7.6 с | 20 |
| **350 (по умолчанию)** | **6.7 с** | **12** |
| 450 | 11.3 с | 23 |

Ниже 250 DPI качество заметно падает, выше 350 — растёт время без выигрыша
(шаблоны начинают хуже попадать в кегль). 350 выбрано по этим замерам.

Внутри одного процесса второй и последующие листы быстрее: шаблоны глифов
кешируются (см. «Кэш шаблонов» ниже). Многостраничный документ обрабатывается
последовательно, поэтому время примерно линейно по числу листов с таблицами.

Три механические оптимизации 2026-09-11 дают побитово тот же результат
(на каждую есть тест сравнения со старой реализацией, `tests/test_speedups.py`):
сравнение маски контура с шаблоном считает все девять сдвигов одной операцией
numpy (`_match_score`, 1,4 млн вызовов на тяжёлом листе); координаты векторных
штрихов переводятся в систему страницы одним матричным умножением, а не по
точке через `fitz.Point` (`map_drawing_arrays`, ~90 тыс. точек на лист); кэш
шаблонов ограничен объёмом, а не числом записей, и переживает перезапуск.

Самые долгие листы — векторные с крупным «взорванным» текстом и гибридным OCR
поверх: на АП 2502-19-РД-КМ1-2 (А3, 4769 глифов, 350 ячеек) уходит ~80 с на
хосте. Раньше было 230 с: шаблоны символов рендерились на холст в девять
кеглей по стороне, и при калибровке кегля (14 кеглей × гарнитуры × кластеры
высот) счёт шёл на десятки тысяч мегапиксельных рендеров; теперь холст тесный
(`_render`). Веб-сервер обрабатывает задания **строго по одному**: два
конвейера в одном процессе на машине с 12 ГБ уходят в своп, и лист «считается»
дольше пяти минут. Второе загруженное задание ждёт в очереди со статусом
`running`; в ответе `/api/job/<id>` у него `phase: "queued"` и `queue_ahead` —
сколько заданий перед ним, интерфейс показывает «В очереди: перед вами N».

### Пределы на одно задание

Чтобы один тяжёлый документ не остановил очередь для всех, у сервиса есть
пределы (переменные окружения контейнера `ocr`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OCRPDF_MAX_PAGES` | 10 | страниц в одном задании; документ длиннее принимается только с полем «Страницы» (`1-3`), иначе ответ 413 с подсказкой |
| `OCRPDF_MAX_SEC_PER_PAGE` | 300 | секунд на страницу; лимит задания = страницы × это значение |
| `OCRPDF_MIN_JOB_SEC` | 600 | но не меньше этого на задание |

Лимит времени проверяется тем же кооперативным флагом, что и кнопка
«Остановить»: перед каждой страницей, блоком и вызовом OCR, поэтому фактическое
превышение — не больше одного блока. Задание, упёршееся в лимит, получает
статус `error` с текстом «превышен лимит времени» и советом выбрать меньше
страниц или снизить DPI. Задания, оставшиеся `running` после перезапуска
процесса (OOM, рестарт контейнера), при старте помечаются ошибкой.

### Кэш шаблонов

Шаблоны глифов (гарнитура × кегль × алфавит) рендерятся из TTF при первом
обращении и кешируются. Калибровка кегля на тяжёлом листе запрашивает около
1100 разных наборов, поэтому кэш ограничен **объёмом**, а не числом записей,
и дублируется на диск: новый процесс (перезапуск контейнера) не рендерит всё
заново. Дисковый ключ учитывает файл шрифта (имя, размер, дата), кегль,
алфавит и версии Pillow/FreeType — чужой или устаревший кэш не подхватится,
битый файл молча удаляется. Запись атомарная; любая ошибка диска отключает
только дисковый слой.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OCRPDF_TEMPLATE_CACHE_MB` | 512 | объём кэша шаблонов в памяти процесса (LRU); полный набор тяжёлого листа — ~370 МБ, на сервере с 2 ГБ на OCR можно оставить, при нехватке памяти снизить до 128–256 |
| `OCRPDF_TEMPLATE_CACHE_DIR` | `<TEMP>/ocrpdf-templates` | папка дискового кэша (один файл `.tpl` на набор: JSON-заголовок и маски, упакованные по битам); пустая строка отключает диск |
| `OCRPDF_TEMPLATE_DISK_MB` | 512 | предел папки; при превышении удаляются самые старые файлы |

В compose папка вынесена в том `ocr-templates`, чтобы кэш переживал
пересборку контейнера.

## 5. Что получается на выходе

```
result/
  page_1_debug.png          страница с рамками таблиц, ячейками и проблемными местами
  table_1.json  .xlsx  .csv  Спецификация металлопроката, «Начало»
  table_2.json  .xlsx  .csv  Спецификация металлопроката, «Окончание»
  table_3.json  .xlsx  .csv  «В том числе по маркам или наименованиям»
  processing_report.json    сводка качества
```

В `debug.png`: синий — рамка блока, серый — ячейка, зелёный — merged-ячейка,
оранжевый — ячейка на ручную проверку, красный — строка, не прошедшая
арифметическую проверку.

XLSX содержит три листа: **«Таблица»** — сетка как на чертеже, с объединёнными
ячейками и подсветкой спорных; **«Плоская»** — построчный вид для расчётов;
**«Проверки»** — все арифметические сверки с пересчётом и допусками.

### Структура JSON

Единица истины — **ячейка**, а не строка. Строки даются вторым,
производным представлением. Так сделано потому, что merged cells физически
принадлежат одной ячейке: в плоской строке их пришлось бы дублировать, теряя
признак «значение взято из объединённой ячейки», а вместе с ним — возможность
корректно считать суммы. Колонки «по элементам конструкции» задаются данными:
их число и названия берутся из шапки листа, а не из схемы.

```jsonc
{
  "document": { "filename": "...", "page": 1 },
  "index": 1, "kind": "spec_main", "part": "начало", "continues_table": null,
  "title": "Спецификация металлопроката",
  "bbox": [144.0, 68.88, 863.88, 1095.12],
  "n_rows": 44, "n_cols": 14, "header_rows": [0, 1, 2],

  "columns": [
    { "index": 3,  "letter": "4",  "role": "position",     "title": "№ п.п." },
    { "index": 4,  "letter": "5",  "role": "element_mass", "element": "Фермы" },
    { "index": 13, "letter": "14", "role": "total_mass",   "title": "Общая масса, т" }
  ],

  "rows": [
    {
      "row": 3, "row_kind": "data", "position": 1,
      "profile_group": "Профили стальные гнутые замкнутые сварные квадратные",
      "profile_group_standards": ["ГОСТ 30245-2003"],
      "steel_grade": "С355-5",
      "steel_grade_standards": ["ГОСТ 27772-2015"],
      "profile_size": "Гн.□160х6",
      "elements": {
        "Фермы": {
          "text": "13,04", "normalized_value": 13.04, "value_kind": "number",
          "page": 1, "bbox": [427.32, 165.24, 469.8, 187.92],
          "confidence": 0.77, "source": "vector_glyph",
          "requires_review": false, "notes": [], "glyphs": []
        },
        "Надколонник": { "text": "", "normalized_value": null, "value_kind": "empty" }
      },
      "total_mass_t": 13.04,
      "source_cells": { "position": { "row": 3, "col": 3, "bbox": [...],
                                      "confidence": 1.0, "source": "text_layer" } },
      "validation": "ok",
      "checks": [ { "kind": "row_sum", "expected": 13.04, "calculated": 13.04,
                    "delta": 0.0, "tolerance": 0.02, "status": "ok" } ]
    }
  ],
  "cells":  [ /* все ячейки сетки, включая шапку и пустые */ ],
  "checks": [ /* все арифметические сверки таблицы */ ]
}
```

Поля, отвечающие требованиям к трассируемости:

* `bbox` + `page` — координаты значения на странице PDF (в точках, origin
  сверху слева);
* `source` — откуда взято: `text_layer`, `vector_glyph`, `ocr`, `mixed`, `none`;
* `confidence` — для текстового слоя 1.0, для векторного распознавания
  минимальный confidence символа в ячейке;
* `requires_review` — ячейку нужно проверить руками;
* `glyphs` — координаты и confidence **каждого символа** плюс альтернативные
  кандидаты. По умолчанию пишутся только для спорных ячеек (для всей страницы
  это лишний ~1 МБ на таблицу); `--all-glyphs` включает для всех;
* `notes` — все применённые правки и замечания.

Пустая ячейка и нуль различаются строго: `value_kind: "empty"` и
`normalized_value: null` против `value_kind: "number"`, `normalized_value: 0.0`.
Неоднозначно распознанное значение не угадывается:

```jsonc
{ "text": "29,?4", "normalized_value": null, "value_kind": "text",
  "confidence": 0.41, "requires_review": true,
  "notes": ["numeric column holds non-numeric text"] }
```

## 7. Результат на исходном тестовом листе

Один лист, CPU, ~10 с. Найдены три логические таблицы:
спецификация «Начало» (41 позиция), «Окончание» (позиции 42–82, со ссылкой
`continues_table: 1`) и «В том числе по маркам или наименованиям» (8 марок).

**Верно распознано всё, что является инженерными данными:** 82 номера позиций,
все обозначения профилей (`Гн.□160х6`, `Гн.□140х60х6`, `t6`…`t34`, `16П`,
`20П`, `24П`, `35К1`, `35Б1`, `L 100х7`, `Н114-750-0,9`, `Крановый рельс КР70`),
все марки стали и ГОСТ, **все значения масс**, строки «Итого» и «Всего
профиля», общий итог 164,96 т и разбивка по маркам. Названия всех девяти
колонок «по элементам конструкции» подняты из шапки (`Фермы`, `Надколонник`,
`Распорки по колоннам`, … `Профнастил покрытия`).

Из 424 непустых ячеек на проверку помечены 12:

* **8 ячеек — из-за ошибки в самом чертеже.** В строке поз. 32 «Итого»
  напечатано `0,63` по колонке «Подкрановая балка» и `4,63` в «Общей массе»,
  тогда как `0,02 + 0,61 = 0,63`. Расхождение тянется в «Всего профиля»
  (поз. 36). Это ошибка исходного документа, а не распознавания — именно для
  таких случаев и нужен слой арифметических проверок. Остальные 144 проверки
  пройдены, включая сверку общего итога по обеим частям листа и суммы по маркам
  (164,97 против напечатанных 164,96 — в пределах допуска на округление).
* **3 описательные подписи** прочитаны с дефектами: `стаяьные` вместо
  «стальные», часть длинного наименования и один заголовок колонки
  (`покрьы+и` вместо «покрытия») в правой таблице. Ни одно числовое значение
  этим не затронуто; все три ячейки помечены `requires_review`.

## 8. Проверено на других листах

Помимо исходного примера конвейер прогнан ещё на трёх документах — все находки
внесены в код.

**КМ1, портретный А1, 17 колонок** (`PIR3017-26-KM1_v6-20.pdf`). Сначала таблица
не находилась вообще. Две причины, обе исправлены:

* линовка таблицы КАСАЕТСЯ рамки листа (вертикаль рамки x = 56.693 пересекает
  горизонтали таблицы, начинающиеся с x = 57). Рамка и таблица попадали в одну
  связную компоненту, её габарит становился размером со страницу, и вся таблица
  отбрасывалась фильтром «это рамка». Теперь линии, тянущиеся почти во всю
  страницу, исключаются из группировки, а пропавшие внешние границы
  восстанавливает `_implied_bounds`;
* в файле есть НЕВИДИМАЯ копия таблицы за пределами листа (половина векторных
  сегментов, x от −1219 до −312). Геометрически это полноценная сетка 83 × 17, и
  она выдавалась за настоящую таблицу. Блоки вне страницы теперь отбрасываются.

Дополнительно: колонка «Площадь окрашиваемой поверхности, м2» получала роль
«масса элемента» и попадала в суммы — сумма по строке выходила 16,79 вместо
0,61. Роль «масса элемента» теперь ограничена строго объединённой ячейкой шапки
«Масса металла по элементам конструкций, т», а для площади добавлена роль `area`,
которая в массовые суммы не входит. Итог: **171 арифметическая проверка пройдена,
расхождений нет**, спорных 9 ячеек из 548.

Осталось неточным: символ типа профиля («Ι» у двутавра, «[» у швеллера, «L» у
уголка) нарисован отдельными штрихами и распознаётся плохо — «Ι 25Ш1» читается
как «25Ш1». Определяющая часть обозначения сохраняется, тип профиля виден из
наименования группы, ячейка помечается на проверку.

**Ведомость объёмов работ** (сгенерированная). Сетка, объединённые ячейки и
значения извлеклись верно; таблица помечена `kind: "generic"`, роли не выдуманы,
проверки не запускались. Нашёлся баг: «Бетонирование фундаментов В25»
превращалось в «825» — правило «буква → цифра» применялось к тексту из
текстового слоя, который точен по построению. Теперь оно работает только с
распознанным текстом, а из карты двойников убраны отличимые пары.

**Спецификация, вставленная как КАРТИНКА** (`Спецификация металла образец.pdf`).
Вся таблица — одно растровое изображение 3184 × 4322 px; векторами нарисованы
только рамка и штамп. Здесь выяснилось, что растровая ветка была подключена не
до конца: OCR-движок принимался в `CellReader`, но не вызывался, а поиск сетки по
растру запускался лишь при полном отсутствии векторных блоков (штамп такой блок
создавал). Теперь таблицы ищутся и ВНУТРИ крупных вставленных картинок, а ячейки
без текстового слоя и векторов читаются OCR.

Результат честный, но частичный: **числа читаются верно** (2,38 / 16,41 / 18,78 /
28,92 / 31,85 … сверено с листом), **кириллица — нет**: RapidOCR транслитерирует
её в латиницу («Итого» → `VTOrO`, «Двутавры стальные» → `ByTaBpbI CTaNIbHble`).
Плюс линовка по растру определяется грубее: 6 колонок вместо 10, часть значений
попадает в соседние ячейки.

Первая версия вызывала OCR на каждую ячейку: 192 вызова и **265 с** на лист.
Теперь область распознаётся ОДНИМ вызовом, а слова раскладываются по ячейкам по
координатам — **14,5 с** при том же результате. Движку к тому же нужен контекст
строки, поэтому так и точнее.

Заодно нашлась ещё одна ошибка классификации: штамп листа (10 колонок, шапка не
читается) получал роли спецификации по позиционному запасному варианту и
выдавался за «Спецификацию металлопроката». Теперь этот вариант требует
распознанной служебной строки нумерации колонок (1, 2, 3, … N).

Чтобы такие листы читались полностью, нужен OCR с кириллицей: Tesseract с
`tessdata` для русского (`--ocr tesseract`) либо ONNX-модель PP-OCR для
кириллицы. Растровая ветка — самая слабая часть PoC, и на сканах её надо
доводить отдельно.

### Листы без текстового слоя, набранные чертёжным шрифтом

Лист КМ (AutoCAD, `PDFium`): текстового слоя нет вовсе, вся графика — осевые
линии, обведённые пером 0.48 pt. Шаблонный распознаватель здесь работает плохо,
и вскрылись две настоящие причины:

* **толщина пера не учитывалась.** Габарит вертикальной стойки «Н» — ширина
  0.03 pt при высоте 7 pt: это осевая линия, чернила появляются только после
  обводки. Габарит теперь расширяется на половину пера (у листов с залитыми
  контурами перо равно нулю, поэтому там ничего не изменилось);
* **Т-образные стыки.** Перекладина «Н» упирается в СЕРЕДИНУ стойки, а
  объединение примитивов шло только по совпадающим концам — буква распадалась
  на три компоненты. Добавлена склейка по перекрытию габаритов.

Проверена и отброшена гипотеза «сравнивать скелеты вместо заливки»: счёт не
вырос, а упал (0.596 против 0.529).

Полностью это лист не вылечило. Рабочим решением для такого класса оказался
**Tesseract с русским**: он читает «ТРУБЫ ПРЯМОУГОЛЬНОГО СЕЧЕНИЯ
ГОРЯЧЕКАТАННЫЕ», «С255 ПО ГОСТ 27772-2021», числа 8549,20 / 15307,99 / 23857,19.
Остаточные ошибки есть («профуля» вместо «профиля», «(255» вместо «С255»).

Поэтому растровый OCR подключается **по качеству, а не по наличию векторов**:
если векторное чтение блока дало больше половины спорных ячеек, блок
перечитывается через OCR, и результат берётся только если спорных стало меньше.
Решение и оба процента пишутся в отчёт:

```
блок [152, 42, 931, 618]: векторное чтение спорно (89%), OCR (tesseract) дал 63% — взят OCR
```

### Гибридный OCR: детектор от RapidOCR, кириллица от Tesseract

Выбирать движок «по листу» не пришлось — на одном и том же листе КМ каждый силён
ровно в своей половине таблицы:

| режим | непустых ячеек | спорных | что не так |
|---|---|---|---|
| `--ocr rapidocr`  | 116 | 5  | ни одного русского слова: `ИТОГО:` → `NTOFO:` |
| `--ocr tesseract` | 66  | 43 | слова верны, но теряются строки и запятые в массах |
| `--ocr hybrid`    | 116 | 21 | остаточные ошибки чертёжного шрифта |

Гибрид устроен не как «два прогона рядом». Выяснилось, что Tesseract на кропе
таблицы половину строк ПРОСТО НЕ НАХОДИТ: `ИТОГО:` в узкой ячейке он пропускает
при любом `--psm`, хотя ту же строку отдельным кропом читает без ошибок. Поэтому
роли разделены:

* **строки ищет RapidOCR** — его детектор находит и то, что Tesseract теряет;
* **читает их Tesseract**, получая ИХ ЖЕ рамки. Все найденные строки собираются
  в одну картинку — по строке в ряд, с белыми зазорами: для Tesseract это уже
  однородный блок, и `--psm 6` разбирает его целиком. Один вызов вместо 109 —
  **0,9 с против 12,6 с**, процесс tesseract стартует дольше, чем читает строку;
* побочная выгода — **общая геометрия**: слова обоих движков гарантированно
  попадают в одну и ту же ячейку.

Чей вариант брать в конкретной ячейке, решает роль колонки (`ENGINE_BY_ROLE`):
наименования и марки — Tesseract, размеры и массы — RapidOCR. Но роли назначаются
по тексту шапки, а шапка сама приходит из OCR искажённой («Наименование» →
«Науменобание»), и колонка нередко остаётся `unknown`. Для неё движок выбирается
по содержимому ячейки (`_resolve_engine`): текст RapidOCR недостоверен, а вот его
СТРУКТУРА достоверна — каждой букве оригинала он подбирает латинскую замену,
каждой цифре верную цифру. Три буквы и больше — слова, отдаём Tesseract; иначе
число или обозначение размера (`□140x5,5`, `L 125x8`, `H60-845-0,8`) — RapidOCR.
Уступаем обратно лишь тогда, когда RapidOCR выдал не число, а Tesseract — чистое
число: так `3869,3`, прочитанное RapidOCR как `E'698E`, не теряется.

Результат на том же листе: `ТРУБЫ ПРЯМОУГОЛЬНОГО СЕЧЕНИЯ ГОРЯЧЕКАТАННЫЕ ПО ГОСТ
32931-2015`, `ИТОГО:`, `НЕУЧТЕННЫЙ МЕТАЛЛ, 2%` — и рядом неиспорченные
`5112,01 / 15307,99 / 23857,19 / 3869,3`. Остаточные ошибки чертёжного шрифта
никуда не делись («профуля» вместо «профиля», `(255` вместо `С255`, `□` как `о`)
— все такие ячейки помечены на проверку.

### Растровая таблица чертёжным курсивом (file-14)

Лист КМ из AutoCAD, где сама спецификация вставлена **картинкой** (JPEG
3168×5404 px, ≈400 dpi) — векторных глифов в таблице нет, текстового слоя
тоже, шрифт ISOCPEUR Italic. Читать её может только растровый OCR, и до
правок он давал «Мm020» вместо «Итого», «(245-4» вместо «С245-4», «JОТ»
вместо «30Б1», «1752.» вместо «17,52»; таблица оставалась `generic`, без
ролей колонок и арифметики. Причины оказались не в движках, а в склейке:

* **пробник шапки читал только Tesseract.** Первые пять строк блока читаются
  «текстом», и служебная строка номеров колонок «1 2 3 … 10» приходила как
  «ий 2 3 4 2 6 … I»: строка не находилась, шапка и роли терялись. Теперь
  движок пробника выбирается по содержимому ячейки (`_resolve_engine`): слова —
  Tesseract, числа — RapidOCR; короткое слово без цифр («т») — тоже Tesseract;
* **слово RapidOCR не попадало в ячейку.** Его рамка выступает за линовку на
  доли пункта, строгая проверка «целиком внутри» её отбрасывала, а перекрытие
  считалось лишь при пустой ячейке. Рамка Tesseract по той же строке (обрезана
  по полосе) оставалась — и ячейка получала «OHO» вместо «0,340», «TT» вместо
  «37,12». Теперь слово принадлежит ячейке, если лежит в ней целиком ИЛИ
  большей частью;
* **курсив.** Tesseract обучен на прямых шрифтах; наклон письма оценивается по
  направлениям штрихов (гистограмма углов градиента без вертикальной
  линовки, `_estimate_slant`), и при наклоне от 7° полосы строк — а также
  повёрнутые подписи шапки и штамп — читаются **дважды**, как есть и
  выпрямленными аффинным сдвигом; для каждой строки берётся вариант, которому
  Tesseract верит больше. Так «Y20/KU CMO/bHbIE» становится «Уголки стальные»,
  «Байки» — «Балки», «ndDHOO» — «Прогоны», а прямой шрифт ничего не теряет.
  Высокая ячейка, в которой OCR по области не нашёл ни слова, теперь сразу
  пробуется с поворотом (раньше такие подписи оставались пустыми);
* **«№ п.п.» не читается** (подпись повёрнута), а роли считались от размера
  профиля — номера позиций попадали в массы по элементам. Колонка сразу за
  размером без словесной подписи считается «№ п.п.»; шапка блока масс
  («Масса металла по зиементам») узнаётся нечётко;
* **после чтения**: служебные строки, опознанные по смыслу, получают подпись
  («Мm020:» → «Итого:», «Вге20 профиия» → «Всего профиля», «„Итого“» →
  «Итого»); «Всего профиля» узнаётся и по геометрии — одна ячейка на три
  графы в строке с массами; скобка перед трёхзначной маркой — это «С», а
  «[ОСТ»/«ГОСГ»/«FОСТ» — «ГОСТ»; цифры марки Tesseract берёт у RapidOCR
  («С215-4» → «С245-4»); в двутаврах «3061» — это 30Б1 (RapidOCR читает «Б»
  как «6»), в уголках «1140х90х8» — L140х90х8 (значок «L» как «1»; снимается,
  только если полка с единицей не существует в сортаменте, «125х8» не
  трогаем).
* **буква серии цифрой** (лист КМ1 л.2, курсив ISOCPEUR): «2051» в двутаврах —
  20Б1 («Б» как «5»; высота сверяется с сортаментом — 20 есть, 205 нет), «227»
  и «167» в швеллерах — 22П и 16П («П» как «7», высота по ГОСТ 8240). Если
  второй движок прочитал букву серии («Т20Б1», «[16П»), берётся его вариант;
  голые цифры без опоры («2011», «352») по-прежнему уходят в варианты

* **значок листа «—»** перед толщиной («—t16», «—14», «—+20») — условное
  обозначение полосы по ЕСКД, в само обозначение не входит: снимается, а
  одинокое число после него в листовой группе становится толщиной («t14»,
  на проверку);
* **вид профиля по стандарту.** Номер ГОСТ/ТУ — цифры, их OCR читает

  160х100, а слово в наименовании ошибочно). Когда словарю не хватает букв

  ГОСТ 19903), имя восстанавливается по стандарту: «Листы стальные

* **скриншот в PDF из Word** («Рама для вентилятора», Obshchaga_KM): лист —

  Lanczos-интерполяцией до масштаба рендера и кладутся на его место

## 9. Ограничения PoC и что проверять на других листах

Честный список, а не формальность.

1. **Ремонт шрифта требует оригинальной гарнитуры в системе.** Если исходный
   шрифт не установлен и сабсет лишён `cmap`, восстановить Unicode нечем.
   Такой шрифт помечается как невосстановимый (`NOT repaired` в отчёте), его
   текст идёт через распознавание глифов. Добавить гарнитуру можно в
   `fontfix.FONT_CANDIDATES`.
2. **Шаблоны глифов рассчитаны на прямое начертание без наклона.** Курсив,
   жирный и одноштриховые чертёжные шрифты (ISOCPEUR, GOST type A) в списке
   референсных гарнитур намеренно отключены: их добавление ухудшило результат —
   близкие по форме варианты начинали выигрывать по метрике и портили
   уверенно читаемый текст. Расширять `glyph_ocr.REFERENCE_FONTS` стоит только
   вместе с замером на реальных листах.
3. **Повёрнутый текст** берётся из текстового слоя (там он читается
   правильно). Распознавание повёрнутых *векторных* надписей не реализовано —
   на этом листе таких нет.
4. **`3` и `З`, `0` и `О` по форме почти неразличимы.** Внутри числовых
   токенов применяется детерминированная замена буквы на цифру (только если
   буква стоит рядом с цифрой, а токен и так содержит цифры); каждая правка
   протоколируется в `notes` вместе с исходным текстом. Вне числовых токенов
   ничего не меняется.
5. **Разделитель размеров** приводится к кириллическому `х`: латинскую `x` и
   кириллическую `х` в растре различить нельзя в принципе.
6. **Пометка части таблицы** («Начало» / «Окончание») сопоставляется по
   закрытому словарю из трёх слов с допуском на неточность — на листе она
   взорвана в векторы и читается как `Окпнчвнив`. Это структурный маркер, а не
   данные.
7. **Растровый резерв проверен на чертёжном листе, но не на настоящем скане.**
   `cv_grid` и `ocr_backends` написаны и подключены, гибридный режим обкатан на
   листе КМ без текстового слоя. На фотографии/скане с шумом и перекосом он не
   проверялся: там ещё понадобятся выравнивание и бинаризация.
8. **Таблицы другого вида извлекаются как сетка, но без семантики.** Роли
   колонок опознаются по тексту шапки. Если шапка не похожа на спецификацию
   металлопроката, таблица помечается `kind: "generic"`: сетка, объединённые
   ячейки, текст и числа извлекаются как есть, роли остаются `unknown`, а
   арифметические проверки НЕ запускаются — придумывать смысл колонок
   некорректно. Проверено на сгенерированной ведомости объёмов работ:
   сетка 6 × 6, объединённая ячейка «Итого» на три колонки и все значения
   извлеклись верно, `kind = generic`, проверок ноль. Чтобы получить для своей
   таблицы семантику и сверку итогов, нужно дополнить `structure.ROLE_PATTERNS`,
   `normalizer.ROW_MARKERS` и правила в `validator`.
9. **Допуск проверок** по умолчанию `max(0.02, 0.006 · n)` т — это учёт
   округления до двух знаков, а не подгонка. Настраивается ключами
   `--tol-base` / `--tol-per-term`.

Что стоит прогнать в первую очередь на других листах: спецификацию с иным
числом колонок «по элементам»; лист, где таблица переносится на **соседнюю
страницу**, а не в соседний блок; чертёж, экспортированный с сохранением
текста (там `vector_glyph` вообще не понадобится); и настоящий скан — чтобы
оценить растровую ветку.

## 10. Встраивание в backend

Есть три способа: HTTP API веб-интерфейса (см. раздел 4), вызов конвейера как
библиотеки и пофазовый доступ.

Конвейер собран как библиотека, CLI и веб-интерфейс — тонкие обёртки над ней:

```python
from ocrpdf.pipeline import Options, run

report = run("input.pdf", "./out", Options(dpi=350, pages="1"))
```

Пофазовый доступ, если файлы на диск не нужны:

```python
import fitz
from ocrpdf.pipeline import Options, process_page

doc = fitz.open("input.pdf")
result = process_page(doc, 0, Options())
for table in result.tables:
    cols = result.columns[table.index]
    rows = result.rows[table.index]
    # table.cells — ячейки с bbox/confidence/source
    # table.checks — арифметические сверки
```

Модули разделены по ответственности и заменяемы независимо: геометрия
(`vector_grid` / `cv_grid`), распознавание (`glyph_ocr` / `ocr_backends`),
семантика (`structure`), проверка чисел (`validator`).
