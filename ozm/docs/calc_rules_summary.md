# Calc rules summary

Подробности реализации: `backend/internal/calc`. Oracle: legacy `ars-A3.xsl`.

## δпр

\[
\delta_{пр} = F / \Pi \quad (\mathrm{mm})
\]

F — площадь сечения (мм²) по семье профиля; Π — обогреваемый периметр (мм) с учётом сторон нагрева.

## ОЗМ (coat=1)

1. Lookup `t500`: base δпр → minute = round(a·(δпр−base)+b) → минимальная толщина плиты с minute ≥ R.
2. lining: 1 короб / 2 контур (тавр/уголок) / 3 round (труба sm + контур).
3. \( V = S_v · (\delta/1000) · q \), \( q = 1.25 \).
4. Сопутствующие: клей 1.2 кг/м² (по площади огнезащиты), штукатурка 3.2 кг/м²
   (по площади облицовки Lh), анкеры 7 шт/м².

## Материалы: справочник и метаданные для ведомости

Расходы, названия и единицы материалов не зашиты в движок, а берутся из
`backend/dicts/materials_rt.json`; справочник генерируется из легаси-выгрузки DC
(`backend/testdata/dc/DC.xml`, блок `<RT>`) командой `dcextract` — Go-версией
(`cmd/dcextract`) или Python-версией (`scripts/dcextract.py`). Атрибуты DC:

| Атрибут DC | Поле JSON | Смысл |
|---|---|---|
| `title`, `unit` | `title`, `unit` | название и единица в ведомости |
| `q` | `q` | коэффициент запаса (ОЗМ 1.25, ОЗБ 1.03) |
| `rate` (текст тега) | `rate` | расход на единицу базы |
| `base="kv"\|"taikor"` | `base` | база расчёта: площадь м² или масса TAIKOR |
| `type="fr_decor"\|"fr_enamel"` | `flag` | материал считается только при флаге элемента |
| `q_min` | `qMin` | минимальный расход на м² (штукатурка 1.5) |
| `δ` | `layerMm` | толщина слоя, мм (грунт 0.1, финиш 0.06) |
| `f="V"\|"M"` | `output` | объём или масса |
| `sort` | `sort` | порядок в ведомости (грунт → состав → финиш) |
| `r="0.###"` | `round` | знаков после запятой при печати |

Правила вывода:

- **штукатурка (`KVer`) — декоративное покрытие**: в ведомость попадает только при
  включённой галочке «Декоративное покрытие Ceresit» (`decor`); для ОЗБ флага нет —
  штукатурка и анкеры считаются всегда;
- расход материала — `max(rate, qMin)`, то есть не ниже минимального;
- порядок строк ведомости — по `sort`, внутри одинакового `sort` — в порядке
  появления материала (у элементов с покрытием TAIKOR: грунт → состав → финиш);
- в строке ответа API отдаются `layerMm` (толщина слоя) и `decimals` (точность
  печати) — их используют ведомость и будущие выгрузки.

## TAIKOR (coat 2/3/4)

Lookup `x500` coat[index] R[min=R] row по δпр.  
\( m = (\Pi/1000)·L · rate · taikor_q \), \( taikor_q = 1.43 \).  
Coat4 может добавить Extra (`heat`).

## АКЗ (coat 1.5)

Конструкция только с антикоррозионной защитой: огнезащитный материал для неё не
считается (состав АКЗ вводится вручную), предел огнестойкости не нужен, но сама
конструкция входит в расчёт — \( S = (\Pi/1000)·L·n \) (площадь окраски), δ и объём
нулевые, строк материалов нет. В итог огнезащиты её площадь не входит (фронт,
`totalsOf`): это площадь АКЗ, а не огнезащиты. До 2026-10-16 такая конструкция
помечалась exclusion «требуется ручной ввод» и не попадала в расчёт.

## Предел огнестойкости R

Не обязателен: у АКЗ его нет вовсе (поле в форме скрыто), у огнезащитного покрытия
может быть не задан («не задан» в списке). Для ОЗМ/TAIKOR без R движок возвращает
exclusion «не задан предел огнестойкости R — укажите его для огнезащитного
покрытия»: молча считать нулевую толщину нельзя. Валидация запроса —
`omitempty,min=15,max=240` (`models.ElementInput`).

## Бетон / ОЗБ

R240 → δ=40 мм (ОЗБ 110); R180 → δ=50 (ОЗБ 80); \( V = S·δ/1000·1.03 \).

## Размеры сечения из справочника проката

Формулы `sectionArea` / `heatedPerimeter` работают с ключами `h`, `b`, `s`, `t` (`R`, `r`, `tr`).
В `dicts/roll.json` формы описаны иначе: квадратная труба — `A`/`s`, круглая — `d`/`h` (здесь `h` — стенка),
уголки — `b`/`B`/`t`, гнутый профиль — `h`/`b`/`t`, тавр — `S`/`S1`/`S2`. Приведение делает `calc.normalizeDims`
(вызывается из `engine.resolveDims`): заполняются только отсутствующие ключи, явные размеры пользователя не меняются,
формулы прежние. До 2026-09-09 приведения не было: у труб и гнутых профилей F ≤ 0 → δпр = 0 → бралась максимальная
толщина покрытия, у уголков считалась половина сечения. Тест: `internal/calc/dims_test.go`.

### Табличные профили CalcLab

Для новых записей `source=calclab-metalloprokat` площадь `F` берётся из
`roll.areaMm2`, если `rollId`, форма и размеры совпадают с табличными. При
ручном изменении размеров применяется геометрическая формула. Прежние записи
не меняют расчётную модель.

Гнутые швеллеры имеют отдельные формы `channel_bent` и `channel_unequal`.
У них постоянная толщина `s`, высота `h`, большая полка `b`, меньшая `b1`
(у равнополочного `b1=b`). Для геометрического контура используются внутренний
радиус `R` и наружный `R+s` — соглашение SVG-модели CalcLab. При нагреве со всех
сторон периметр `2h+2(b+b1)-2s+(π-4)(2R+s)`; меньшая полка располагается сверху.
Это геометрия контура, а не подмена профильного ГОСТа или методики `t500`/`x500`.

В импорте OCR стандарт спецификации используется для выбора новой записи и
её табличной массы. Если одному размеру соответствуют две таблицы гиба с
разной массой, автоматический выбор массы не выполняется.

## Источник дополнения сортамента

`docs/calclab-sortament-comparison.json` — сравнение и контрольные суммы
источников. `backend/scripts/sync-calclab-sortament.mjs` импортирует именно
видимую модель `/references/metalloprokat` из локального клона CalcLab:

```powershell
node backend/scripts/sync-calclab-sortament.mjs D:\dev\calclab.pro
node backend/scripts/sync-calclab-sortament.mjs D:\dev\calclab.pro --write
```

Первая команда только сравнивает. Источники не изменяются; неизвестные формы
и строки, исключённые самим справочником CalcLab, не добавляются. Миграция
`0008` дополняет базу ОЗМ, сохраняя пользовательские записи.
